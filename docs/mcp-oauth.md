# MCP с доменным входом через браузер

DevRefresh принимает удалённые MCP-запросы по Streamable HTTP на `/mcp`. На рабочую станцию не нужно устанавливать отдельный клиент DevRefresh: нужен AI-клиент с поддержкой удалённого MCP, OAuth Authorization Code, PKCE S256 и динамической регистрации public clients.

## Настройка службы

1. Настройте прямой HTTPS-доступ к службе и доверенный сертификат по [руководству установки](../deploy/portable/README.md). Windows-аутентификация должна работать в браузере по этому же адресу. Имя DNS, сертификат и SPN для Kerberos настраиваются администратором инфраструктуры.
2. В существующий `config/server.json` добавьте:

```json
{
  "Mcp": {
    "Enabled": true,
    "PublicUrl": "https://devrefresh.example.com:5189",
    "AllowedRedirectUris": []
  }
}
```

`PublicUrl` — точный внешний HTTPS-адрес корня этой службы, включая порт, если он нестандартный. Адреса с путём, query string, фрагментом или учётными данными не принимаются. `AllowedHosts` и HTTPS endpoint в существующей конфигурации также должны соответствовать этому имени. Перезапустите службу после изменения конфигурации. По умолчанию MCP выключен.

Callback native-клиента на `http://127.0.0.1:<port>/...`, `http://localhost:<port>/...` или `http://[::1]:<port>/...` разрешён для локального слушателя клиента. Если клиент возвращается на внешний HTTPS-адрес, добавьте **полный точный callback URL** в `AllowedRedirectUris`. Шаблоны и произвольные внешние адреса не разрешены. В список нужно вносить адрес, указанный документацией конкретного клиента.

AI-клиенту необходим сетевой доступ к HTTPS-адресу службы. Доступ с рабочей станции возможен через корпоративную сеть/VPN. Для облачного клиента требуется отдельно обеспечить сетевую доступность; OAuth сам по себе VPN не заменяет. Поддержка прокси, завершающего TLS, в эту версию не добавлялась: служба проверяет HTTPS и канонический Host напрямую.

## Подключение пользователя

1. В настройках MCP-клиента добавьте remote HTTP server: `https://devrefresh.example.com:5189/mcp`.
2. Выберите OAuth-вход. Клиент обнаружит сервер авторизации и зарегистрирует своё приложение.
3. В открывшемся браузере подтвердите Windows-вход. Служба получает доменное имя и Windows SID через Negotiate. Локальная учётка администратора не заменяет доменную идентичность для OAuth.
4. На странице согласия проверьте имя клиента, callback URL, свою доменную учётку и запрашиваемые разрешения. Нажмите «Разрешить».
5. Клиент получит токены автоматически. Пароли AD/SQL и токены не нужно передавать в чат.

Разрешения: `devrefresh.read` — просмотр; `devrefresh.restore` — подготовка и запуск восстановления. Для длительного подключения клиент дополнительно запрашивает `offline_access`. `devrefresh.read` обязателен. OAuth не предоставляет прав на чужие базы: действуют текущие роли интерфейса и общий список операторов `_tk`.

Пользователь видит свои разрешённые подключения на вкладке **«Подключения MCP»** и может отозвать любое из них. Отзыв блокирует следующие запросы и обновление токенов. Уже запущенное задание продолжает работу. Глобальное отключение доменного входа запрещает существующим OAuth-подключениям дальнейшие обращения. Изменение ролей devRefresh учитывается при каждом запросе и перед изменением целевой базы. Состояние блокировки учётки непосредственно в AD не опрашивается на каждом Bearer-запросе.

## Методы

| Метод | Параметры | Результат |
| --- | --- | --- |
| `get_identity` | Нет | Доменная учётка и текущие права |
| `list_databases` | Нет | Доступные базы назначения |
| `get_restore_options` | `database` | Архивы, даты, размеры, источники, соединения |
| `list_copy_sources` | `database` | Подходящие Dev-базы того же типа |
| `prepare_restore` | `database`, `mode`, необязательный `source_database` | План на пять минут или запрос выбора источника |
| `start_restore` | `plan_id`, `confirm_replace`, `confirm_disconnect`, `request_id` | Поставленное в очередь задание |
| `get_job` | `job_id` | Состояние, текущий этап и результат |

SDK может помещать полезный результат инструмента в `structuredContent.result`; текстовое представление содержит те же данные.

Режимы `mode`: `shrink`, `full`, `dt`, `developer_copy`. Если Full отсутствует, выбирается `.dt`; если `.dt` отсутствует, выбирается Full. Каталог и способ восстановления должны быть корректно настроены. Ошибка чтения/настройки не считается отсутствием архива. После начала восстановления автоматических повторов другим способом нет. Для Shrink автоматической замены нет.

Для `developer_copy` требуется явно выбранная пользователем база-источник. Если `source_database` не передан, метод возвращает `status=source_required`, вопрос и список источников, даже при единственном кандидате. Строки «копия другого разработчика» недостаточно для запуска. Если пользователь уже указал полное имя источника, повторно спрашивать его не нужно.

План показывает фактический формат, причину замены формата, архив и дату данных, активные подключения и операции после восстановления. Для `.dt` отмечено, что целевая SQL-база будет удалена перед IBCMD create. Используются операции формата фактически выбранного архива.

Запуск разрешён только по явному запросу пользователя заменить содержимое базы. Завершение активных соединений требует отдельного разрешения, если оно не дано в исходном запросе. `request_id` — UUID. Один план может создать только одно задание, включая одновременные повторы запроса и повтор после обрыва соединения. План связан с конкретным OAuth-подключением; другой grant того же пользователя не может его использовать.

Архив фиксируется именем, размером и временем изменения; замена/исчезновение файла, изменение настроек SQL, соответствия типов или операций делают план недействительным. Права и выбранный источник проверяются снова перед изменением целевой базы. Для Dev-копии фиксируется выбранная база, а её данные копируются на момент фактического BACKUP.

**Проверка свободного места на SQL пока не реализована.** План возвращает `diskSpaceCheck=not_implemented`. Это ограничение сохраняется для всех способов восстановления.

## Протокол и хранение

Реализация использует OpenIddict 7.9 и официальный MCP C# SDK 2.4. Авторизация: Authorization Code + обязательный PKCE S256, одноразовый код на две минуты, opaque reference access token на десять минут, rotating refresh token на 14 дней. Пользовательские права не фиксируются в токене навсегда. Входящие токены предназначены только для канонического `/mcp` этой службы; SQL использует отдельное служебное подключение.

Endpoints: `/.well-known/oauth-protected-resource/mcp`, `/.well-known/oauth-authorization-server`, `/oauth/register`, `/oauth/authorize`, `/oauth/token`, `/oauth/revoke`, `/mcp`. Public clients регистрируются с `token_endpoint_auth_method=none`. OAuth confidential clients и Client ID Metadata Documents в первой версии не реализованы. DCR и token endpoint ограничены по частоте запросов. Callback проверяется по allowlist; приложение не скачивает URL клиента.

Все секреты находятся в каталоге данных установленной службы: `mcp-oauth.sqlite`, `mcp-keys.protected` и существующий каталог `keys`. Ключи подписи/шифрования MCP защищены ASP.NET Data Protection, а его ключи — Windows DPAPI и ACL каталога. Они сохраняются при перезапуске. SQL-пароли не выдаются MCP-клиенту. База `devrefresh.sqlite` имеет схему 14 из-за планов и нового формата заданий.

Штатное обновление дополнительно сохраняет снимок OAuth SQLite и защищённый файл ключей в приватной резервной копии. При откате OAuth-хранилище сохраняет текущее состояние, чтобы не возвращать ранее отозванные подключения. Для ручной аварийной копии сохраняйте весь каталог данных и его ACL. Эти файлы, журналы и резервные копии нельзя добавлять в публичный репозиторий или дистрибутив.

## Проверка

Автоматические тесты проходят OAuth exchange и настоящие MCP-вызовы через официальный SDK без изменения SQL-баз. Windows principal в тестах подставляется только тестовым middleware, отсутствующим в приложении. Реальный вход Negotiate/Kerberos нужно проверить на доменной рабочей станции по настроенному DNS/HTTPS-адресу.

Источники: [MCP authorization](https://modelcontextprotocol.io/specification/latest/basic/authorization), [OpenIddict server](https://documentation.openiddict.com/guides/getting-started/creating-your-own-server-instance), [OpenIddict validation](https://documentation.openiddict.com/guides/getting-started/implementing-token-validation-in-your-apis).
