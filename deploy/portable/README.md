# DevRefresh 0.2.45 — служба Windows x64

## Быстрый запуск на другом сервере

1. Перенесите ZIP на сервер и **полностью распакуйте** его, например в `C:\DevRefresh`. Не запускайте EXE прямо из окна архива.
2. Запустите **STARTSERVICE.cmd от имени администратора Windows**. Если службы DevRefresh ещё нет, скрипт подготовит каталоги, создаст службу с автоматическим запуском и запустит её. Если она установлена, только запустит; если уже работает — сообщит об этом.
3. На этом сервере откройте **http://127.0.0.1:5188/login**. Создайте первого администратора, затем заполните настройки SQL и каталогов бэкапов в админке.
4. Окно скрипта можно закрыть. Приложение работает в фоне и автоматически запускается после перезагрузки Windows. Для остановки запустите **STOPSERVICE.cmd от имени администратора**. Он только останавливает службу: если она не установлена или уже остановлена, выводит сообщение. Служба, настройки и данные сохраняются.

Служба называется `DevRefresh`, отображается как `DevRefresh`, при создании работает под **Local System (LocalSystem)** без ввода логина и пароля. Учётную запись можно изменить в `services.msc → DevRefresh → Свойства → Вход в систему`. При последующих запусках STARTSERVICE учётная запись существующей службы сохраняется. Размещайте приложение в постоянной папке; после установки не переносите её.

При переходе с START.cmd сначала остановите прежний процесс Ctrl+C. Первый STARTSERVICE запускайте с повышенными правами **под тем же Windows-пользователем**, который ранее запускал приложение: он переведёт существующие DPAPI-ключи в режим LocalMachine, проверит чтение сохранённого SQL-пароля и сохранит SQLite. Пароль администратора сайта, настройки и профили остаются прежними. Доступ к ключам ограничивается службой, SYSTEM, администраторами Windows и пользователем установки. Между разными серверами DPAPI-ключи этим способом не переносятся.

После ручной смены учётной записи предоставьте выбранному пользователю чтение папки приложения, config и бэкапов, изменение каталогов data (включая keys) и logs, а при HTTPS — чтение закрытого ключа сертификата. DPAPI-ключи подготовлены в режиме LocalMachine, повторно вводить SQL-пароль на этом же сервере не требуется при сохранении ключей и прав на них. Для сетевой папки используйте UNC-путь: подключённые пользователю диски служба не видит. LocalSystem в домене обращается к сетевым ресурсам от имени компьютера `DOMAIN\SERVER$`; при доменном пользователе доступ назначается этому пользователю. При SQL-аутентификации используется сохранённый SQL-логин. Доступ SQL Server к .bak настраивается отдельно для его службы.

В комплекте есть `app\DevRefresh.exe` со встроенной средой .NET. Устанавливать .NET SDK, .NET Runtime, IIS, Python, Node.js или SQLite отдельно для этого способа запуска не требуется. Интернет для запуска не нужен. Нужна Windows x64 с поддержкой .NET 10; версия Windows Server должна быть проверена по таблице Microsoft. Пакет предназначен для Windows Server 2016/2019/2022/2025 и актуальной Windows 11; фактический запуск на вашем сервере проверяется командой CHECK.

Если политика организации блокирует запуск неподписанных EXE или PowerShell-скриптов, примените принятый у вас порядок допуска приложения. Батники диагностики используют штатный Windows PowerShell 5.1. Изменение политики PowerShell выполняется только для процесса батника; системная политика не меняется.

## Доступ сотрудников по сети

Первичный запуск доступен только на самом сервере. Для сетевого доступа используйте корпоративное DNS-имя и HTTPS:

1. Установите подходящий серверный сертификат с закрытым ключом в `LocalMachine\My`. Имя сайта должно присутствовать в DNS-именах сертификата, а клиенты должны доверять его цепочке. Учётной записи запуска нужен доступ к закрытому ключу.
2. Запустите **SETUP-HTTPS.cmd** и укажите корпоративное DNS-имя и SHA-1 отпечаток сертификата. Скрипт не создаёт самоподписанный сертификат и не запрашивает пароль закрытого ключа.
3. Выполните STOPSERVICE, затем STARTSERVICE. Сайт будет доступен по `https://имя-сервера:5443/`; локальная админка останется на `http://127.0.0.1:5188/login`.
4. Настройте DNS и разрешите входящий TCP 5443 в серверном/сетевом межсетевом экране. Сам скрипт правила сети не меняет.

Из PowerShell можно задать другой HTTPS-порт и хранилище сертификатов:

```powershell
.\scripts\Configure-Https.ps1 -DnsName devrefresh.company.local -Thumbprint 0123456789ABCDEF0123456789ABCDEF01234567 -Port 5443 -StoreLocation LocalMachine
```

Корпоративный вход использует Negotiate и требует проверки в доменном окружении через Edge/Chrome. Сервер, браузеры и DNS-имя должны быть настроены для Windows Authentication. Главная страница по умолчанию показывает обычную форму входа. На домашнем компьютере задайте в config/server.json параметр WindowsAuthentication.Enabled в false; автоматический корпоративный вход включается отдельным параметром WindowsAuthentication.AutoSignIn: true. Для локального администратора всегда доступен /login. После изменения конфигурации выполните STOPSERVICE, затем STARTSERVICE. Не меняйте URL на сетевой HTTP: приложение принимает удалённый доступ только по HTTPS.

## Если произошла ошибка

1. Запустите **CHECK.cmd** — он покажет версию EXE, архитектуру Windows, параметры запуска и ответ `/health`. Код возврата 0 означает, что локальный `/health` ответил успешно; 1 — что проверка не пройдена.
2. Воспроизведите ошибку и запомните действие, время и «Код обращения», если он появился на сайте.
3. Запустите **COLLECT-LOGS.cmd**. В папке `support` появится **DevRefresh-support-…zip**. Отправьте этот ZIP вместе с описанием действия и временем ошибки.

Архив содержит отчёт о среде, последние 7 файлов журналов и последние 1000 строк журнала запуска. Он не собирает SQLite, ключи шифрования, сертификаты, конфигурацию сервера целиком и переменные окружения. Журналы не записывают тела HTTP-запросов, SQL-пароли или cookies; в них присутствуют технические пути, время, коды ошибок, версия и идентификаторы запросов.

При ошибке до старта приложения смотрите `logs\launcher.log`. Основной журнал `logs\devrefresh-YYYYMMDD.jsonl` делится по датам и при достижении 10 МБ. В разделе «Настройки → Журналы DevRefresh» можно задать срок хранения этих файлов в днях. По умолчанию срок составляет 14 дней. Сервис удаляет файлы журнала по времени последней записи при запуске и затем раз в час. Время в JSON-журнале содержит смещение часового пояса.

Диагностическая сборка пишет события `SQL diagnostic` при свёртке. Они содержат идентификатор задания, таблицу, время и номер порции, число строк, счётчики чтения, ожидания SQL Server, расход журнала транзакции и доступные операторы плана. Для разбора запустите `COLLECT-LOGS.cmd` и приложите архив вместе с идентификатором задания.

Для чтения состояния SQL-сессии используемой SQL Server учётной записи требуется `VIEW SERVER PERFORMANCE STATE` на SQL Server 2022 и новее либо `VIEW SERVER STATE` на SQL Server 2019 и старше. Без этих прав доступны тайминги команд, порции и ошибки. Чтобы выключить подробную диагностику, добавьте в `config\server.json` секцию `"SqlDiagnostics": { "Enabled": false }` и перезапустите службу.

EXE можно запустить напрямую из папки `app`: он сам найдёт соседний `config\server.json`. Для диагностики ранних ошибок рекомендуется START, поскольку он сохраняет stdout/stderr в launcher.log.

## Структура и обновление

```text
STARTSERVICE.cmd          установка при отсутствии и запуск службы
STOPSERVICE.cmd           только остановка службы
START.cmd                 консольный запуск для диагностики (при остановленной службе)
UPDATE.cmd                обновление существующей установки
UPDATE-ONLINE.cmd         обновление из GitHub Releases
ROLLBACK.cmd              откат обновления
CHECK.cmd                 проверка
COLLECT-LOGS.cmd          архив для разбора ошибок
SETUP-HTTPS.cmd           подключение установленного сертификата
app/                      заменяемые файлы приложения
config/server.json        параметры запуска вашего сервера
scripts/                  вспомогательные скрипты
BUILD-INFO.json            версия и контрольная сумма EXE
data/                     создаётся при запуске: SQLite и ключи
logs/                     создаётся при запуске: журналы
support/                  создаётся при сборе диагностики
```

Для обновления:

1. В установленной папке выполните **STOPSERVICE.cmd**. Дождитесь сообщения об остановке; не обновляйте приложение во время задания.
2. Распакуйте ZIP новой версии в отдельную папку и выполните из неё **UPDATE.cmd** от имени администратора, указав путь к существующей установке. Скрипт сохраняет резервную копию, обновляет файлы приложения и выполняет миграции SQLite. Конфигурация сервера, рабочая БД и ключи хранятся в существующей установке.
3. В **существующей папке установки** выполните **STARTSERVICE.cmd**, затем **CHECK.cmd**. Переустановка службы не нужна.

При первом переходе со старой версии, где STOPSERVICE ещё нет, остановите консольный процесс Ctrl+C, затем выполните пункты 2–3. Не распаковывайте установочный архив поверх рабочей конфигурации.

Начиная с 0.2.39 можно запускать `UPDATE-ONLINE.cmd` от имени администратора из папки установки. Скрипт проверяет последнюю стабильную версию в [GitHub Releases](https://github.com/Xelgo/devrefresh/releases), скачивает ZIP и сверяет SHA-256 до остановки службы. Подтверждайте установку в окно обслуживания, поскольку остановка может прервать задания. После установки скрипт запускает службу, если она работала до обновления. `UPDATE-ONLINE.cmd -CheckOnly` проверяет наличие новой версии. Серверу нужен доступ по HTTPS к GitHub API и загрузкам GitHub Releases.

С 0.2.41 администратор сайта может проверить версию и список изменений в разделе «Настройки → Обновление DevRefresh». Кнопка установки доступна, если DevRefresh запущен как служба Windows под LocalSystem или учётной записью с правами администратора Windows. После подтверждения служба скачивает пакет, проверяет его, останавливается и запускается на новой версии. Выполняющиеся задания нужно дождаться, задания в очереди сохраняются. Для установки кнопкой службе нужен исходящий HTTPS-доступ к GitHub. Отключить установку из интерфейса можно параметром `"Updates": { "Enabled": false }` в `config/server.json`.

Служба завершает приложение штатно; ожидание остановки — до 150 секунд, тайм-аут остановки фоновых операций приложения — 120 секунд. При ошибке скрипт возвращает ненулевой код. Журналы приложения находятся в настроенной папке logs; CHECK и COLLECT-LOGS включают состояние службы. Для диагностики раннего сбоя используйте журнал Windows и START.cmd при остановленной службе.

Сборка не содержит настроек SQL или администратора с компьютера разработки. Она запускается с чистой настройкой.

## Что входит в версию

Админка, SQLite с миграциями, подключение к Dev SQL, обнаружение баз и бэкапов, восстановление выбранной Dev-базы, анализ таблиц, профили сокращения, расписание подготовки Shrink-копий, индикаторы заданий и аудит. Работа как служба Windows. Обезличивание остаётся отдельным незавершённым сценарием.

Документация платформы: [автономные сборки .NET](https://learn.microsoft.com/en-us/dotnet/core/deploying/single-file/), [поддерживаемые ОС .NET 10](https://github.com/dotnet/core/blob/main/release-notes/10.0/supported-os.md).

## Корпоративный доступ и восстановление

Корпоративный вход и автоматический доменный вход настраиваются в интерфейсе «Настройки → Доступ администраторов» и сохраняются в SQLite без перезапуска. server.json задаёт начальные значения до первого сохранения в интерфейсе.

Сервис подбирает файл по типу базы и самой свежей дате в имени. Например, для `bp_mko_dev_demo_owner` подходит `bp_mko_11-11-2026.bak`. При отсутствии датированных файлов используется `bp_mko.bak`. Для анализа администратор выбирает конкретный файл.

Если типы отличаются, добавьте соответствие в разделе «Анализ и сокращение» → «Соответствия бэкапов». Например, `ut_ke → ut` позволяет обновлять базы `ut_ke_dev_*` из копий `ut`. Чтобы настроить сокращение, проанализируйте копию `ut` и сохраните профиль для типа Dev-базы `ut_ke`.

Восстановление идёт напрямую в выбранную Dev-базу. Предыдущая база и подготовительные .bak не копируются, автоматического отката нет; при ошибке смотрите журнал задания и логи. Временные SQL-базы анализа удаляются после завершения, ошибки или прерывания; после аварийной остановки очистка повторяется при запуске. Если SQL недоступен, повтор очистки выполняется каждые 30 секунд.

## Прогноз свёртки

Для Shrink-копий укажите отдельную папку в настройках. Службе SQL Server нужны права на запись и чтение файлов, службе DevRefresh — на чтение и удаление. Настройте дни недели и время сервера в разделе «Анализ и сокращение → Расписание Shrink». Для готовой копии показываются дата данных и размер архива.

При сборке Shrink DevRefresh очищает связанные блоки `BinaryData` для полностью очищаемых таблиц. Он собирает ключи из распознанных указателей в этих таблицах и удаляет блоки, если в оставшихся двоичных полях не найден указатель на тот же ключ. Отчёт задания показывает число блоков и объём их содержимого.

## Прогресс на главной

На главной каждое активное задание показано отдельной строкой с текущим этапом. Прогресс восстанавливаемой базы оценивается по истории успешных запусков той же базы и режима свёртки. Без истории видно прошедшее время. При успехе полоса доходит до 100%, отметка остаётся на пять минут. Полная история доступна в разделе «Задания».

Одновременно выполняются до двух заданий разных типов баз. Для изменения общего лимита задайте `MaxParallelJobs` в разделе `Workflows` файла `config/server.json` и перезапустите службу. При значении `1` все задания выполняются последовательно.

В окне актуализации можно выбрать другую Dev-базу того же типа на этом SQL Server. SQL Server создаёт временный сжатый `COPY_ONLY`-бэкап, восстанавливает его в базу назначения, а DevRefresh удаляет файл. База-источник остаётся доступной. Соединения с базой назначения завершаются при замене после подтверждения в интерфейсе.

В разделе «Настройки» можно указать две записи для одной папки: путь к временным `.bak` со стороны DevRefresh и путь со стороны SQL Server. Если оба поля пусты, используются пути к каталогу Shrink-копий. Учётной записи службы SQL Server нужны права на запись и чтение в папке, а службе DevRefresh — на чтение и удаление временных файлов. Убедитесь, что в папке достаточно места для `.bak`.

После восстановления служба устанавливает `SIMPLE`, выполняет `CHECKPOINT` и включённую в настройках проверку целостности, затем открывает базу для работы. Слот восстановления освобождается после открытия доступа. Освобождение места выполняется в отдельной очереди по одной базе за раз с низким приоритетом блокировок на SQL Server 2022 и новее. Следующее фоновое сжатие стартует, когда основная очередь свободна. Пока выполняется фоновое сжатие, можно восстановить другую базу, в том числе того же типа. Повторное восстановление той же базы ждёт завершения её сжатия. На более ранних версиях SQL Server фоновый этап пропускается. Статус и время открытия базы видны в отчёте задания. При сборке Shrink-архива освобождение места выполняется до записи `.bak`.
